# 1C:Fresh ЭСФ — OData, фаза 1

> **Codex migration handoff (26.10.2026):** read [`AGENTS.md`](AGENTS.md), [`docs/SPEC.md`](docs/SPEC.md), [`docs/STATUS.md`](docs/STATUS.md), [`docs/DECISIONS.md`](docs/DECISIONS.md) and [`docs/ROADMAP.md`](docs/ROADMAP.md) first. The sections below document earlier development phases and may refer to them as current. A narrowly scoped single-record production contract PATCH was later implemented and successfully verified; **the full invoice/receipt workflow is not implemented**. No further live writes are preauthorized.

Безопасный прототип для изучения OData конфигурации «Бухгалтерия для Казахстана», ред. 3.0. Использует только стандартную библиотеку Python 3.12+; ничего не записывает в 1С. В коде нет POST/PATCH/PUT/DELETE и нет автоматического изменения прав доступа.

## Dry-run процессор (фаза 2)

Теперь проект включает `main.py`, `config.py` и чистый планировщик
`processor/planner.py`. **Никаких HTTP-запросов записи по-прежнему нет.**
Планировщик составляет действия, но не исполняет их.

Сначала можно полностью офлайн проверить один реальный ЭСФ по уже сохранённым
отчётам (команда не требует учётных данных):

```powershell
python main.py plan-one --preflight "esf_preflight_v2.json" --contracts "contract_lookup.json" --output "dryrun_one.json"
```

Для небольшой партии из текущего списка — `pending_transavia.json` должен
содержать явные `organization_key` и `counterparty_key`, а переменные авторизации должны быть
заданы в текущем PowerShell. Команда перечитывает каждый ЭСФ через GET:

```powershell
python main.py plan-batch --pending "pending_transavia.json" --contracts "contract_lookup.json" --expected-from-date 2026-09-21 --expected-to-date 2026-10-13 --limit 5 --output "dryrun_five.json"
```

После проверки первых пяти можно увеличить `--limit` (максимум 200). Партия
обрабатывается в порядке записей в JSON; неподходящие и недоступные документы
помечаются `blocked`, `read_error` или `skip_already_linked`.

В каждом плане есть:

- `ready_for_review` — реквизиты достаточны для рассмотрения проекта изменений,
  **это не разрешение на выполнение и не гарантия доступности OData-проведения**;
- `blocked` — обнаружена неоднозначность или отсутствует нужный реквизит;
- `skip_already_linked` — связанный счёт-фактура уже существует;
- `read_error` — документ не удалось заново прочитать или сверить.

Действия `prepare_*` — **намерения**, а не исполняемые HTTP-команды. Отдельно
потребуется проверить 1С-команды создания на основании, перезаполнения
ссылочных реквизитов и проведения. Время у вновь создаваемых документов
планируется как `10:00:00`; существующая дата каждого документа должна быть
прочитана на этапе исполнения, а не подставлена заранее.

Все записи выполняются отдельно и только после будущего согласования.

## Текущий приоритетный прототип: один поставщик

Целевой сценарий до дальнейшего согласования бизнес-правил:

- **Поставщик:** ТОО «Трансавиа»;
- **Период включительно:** 21.09.2026–13.10.2026;
- **Договор:** `ALA-58/2025 SD`;
- **Организация:** `57495537-f978-11ee-ad65-94de80502ae1` (из проверенного ESF);
- остальные поставщики, периоды и договоры не обрабатываются этим прототипом.

Перед запуском **обязательно подтвердить** GUID поставщика. Владелец найденного
договора `ALA-58/2025 SD` имеет GUID
`b711f358-7da3-11f0-8757-52540067a9c9`, но по одному GUID мы ещё не
доказали, что это ТОО «Трансавиа». Прочитать представление контрагента:

```powershell
python odata_client.py sample --entity "Catalog_Контрагенты" --filter "Ref_Key eq guid'b711f358-7da3-11f0-8757-52540067a9c9'" --fields "Ref_Key,Description" --show-values --output counterparty_check.json
```

Если `Description` совпадает с нужным юридическим лицом, запускайте узкий
сканер (вместо старых широких октябрьских отчётов):

```powershell
python esf_scanner.py --from-date 2026-09-21 --to-date 2026-10-13 --organization-key "57495537-f978-11ee-ad65-94de80502ae1" --counterparty-key "b711f358-7da3-11f0-8757-52540067a9c9" --output pending_transavia.json
```

Потом можно построить первые пять планов:

```powershell
python main.py plan-batch --pending "pending_transavia.json" --contracts "contract_lookup.json" --expected-from-date 2026-09-21 --expected-to-date 2026-10-13 --limit 5 --output "dryrun_transavia_five.json"
```

`plan-batch` для текущего прототипа требует `counterparty_key` в исходном
отчёте и проверяет его против `Owner_Key` договора и `Контрагент_Key` каждого
ЭСФ. Параметры не зашиты в алгоритм: позднее можно подключить другие
профили поставщиков, даты и правила назначения договоров.

## Первый исполнитель: только один договор в одном ЭСФ

`execute_contract.py` — изолированный компонент для **единственного PATCH**
по полю `ДоговорПоставки_Key` в одном выбранном ЭСФ. Программа перепроверяет
текущий документ через GET, номер, дату, организацию, поставщика, отсутствие
связанного СФ и готовность dry-run плана. Она не создаёт документы, не
перезаполняет табличные части и не проводит ничего.

На первом запуске **используйте только preview**, без `--commit`:

```powershell
python execute_contract.py --pending "pending_transavia.json" --contracts "contract_lookup.json" --ref-key "e3ce4858-c61b-11f1-9a8a-52540009ca86" --number "28000019906"
```

Режим реальной записи в программе существует, но требует одновременно
`--commit` и отдельной фразы-подтверждения с точным номером ЭСФ. **До
согласования результата preview не включайте его.** После отправки PATCH
программа перечитывает ссылку. При ошибке сети нельзя просто повторять
запрос: сервер мог уже сохранить изменение.

При изменении табличной части 1С OData требует передавать её полное
содержимое, поэтому будущий исполнитель товаров будет отдельным модулем
с гораздо более строгими проверками. Команды создания на основании и
проведения также будут разрабатываться и испытываться отдельно.

## Следующая фаза: поиск эталона связанного полученного СФ

После успешного единичного PATCH договора изучаем уже существующие документы,
созданные в 1С штатным способом. Это позволит сверить реальные связи и
состав табличных частей перед первым POST нового счёта-фактуры:

```powershell
python reference_inspector.py --from-date 2026-09-21 --to-date 2026-10-13 --organization-key "57495537-f978-11ee-ad65-94de80502ae1" --counterparty-key "b711f358-7da3-11f0-8757-52540067a9c9" --limit 1 --output "reference_invoice.json"
```

Это исключительно GET-запросы. Отчёт показывает номер и дату ЭСФ, связь
с полученным счётом-фактурой, реквизиты полученного СФ и структуру табличных
частей. Если стандартный OData хранит ссылку не как обычный GUID, инспектор
явно помечает её как требующую дальнейшей расшифровки.

## Подготовка

1. Убедиться, что в настройках OData опубликованы необходимые объекты и у используемой учётной записи есть право API-доступа.
2. В терминале **локального компьютера** задать переменные окружения `ONEC_ODATA_USERNAME` и `ONEC_ODATA_PASSWORD`, не записывая пароль в код или команды, попадающие в историю оболочки. Использовать защищённый ввод или системное хранилище секретов.
3. При необходимости задать `ONEC_APP_URL`. По умолчанию используется URL известной базы без секретов.

```bash
python odata_client.py entities --match "Электрон"
python odata_client.py entities --match "Счет"
python odata_client.py entities --match "Поступление"
```

Результат покажет **реальные OData EntitySet**, а не предполагаемые имена по надписям в 1С.

Для проверки схемы одного документа:

```bash
python odata_client.py sample --entity ТОЧНОЕ_ИМЯ_ИЗ_ENTITIES
```

Для просмотра типов всех полей непосредственно из `$metadata` (без чтения записей):

```bash
python odata_client.py schema --entity "Document_ЭСФ"
python odata_client.py schema --entity "Document_СчетФактураПолученный"
python odata_client.py schema --entity "Document_ПоступлениеТоваровУслуг"
```

В Windows PowerShell 5.1 не используйте `>` для русскоязычного JSON: это может
исказить кириллицу. Команда `--output` сохраняет UTF-8 напрямую из Python:

```powershell
python odata_client.py schema --entity "Document_ЭСФ" --output esf_schema.json
python odata_client.py schema --entity "Document_СчетФактураПолученный" --output invoice_schema.json
python odata_client.py schema --entity "Document_ПоступлениеТоваровУслуг" --output receipt_schema.json
```

Выборочно прочитать связанные реквизиты только одного ЭСФ (содержит реальные
значения; перед отправкой вывода удалите конфиденциальные данные):

```powershell
python odata_client.py sample --entity "Document_ЭСФ" --fields "Ref_Key,Number,Date,СчетФактура,СчетФактура_Type" --show-values
```

## Поиск ЭСФ без связанного счёта-фактуры

Сканер делает только GET и **не наследует фильтры открытого списка 1С**.
Дата начала и конца задаётся явно; подставляйте только период, который
сверили с интерфейсом. Организацию при необходимости ограничьте GUID:

```powershell
python esf_scanner.py --from-date 2026-10-01 --to-date 2026-10-31 --output pending_esf.json
```

Дополнительно `--organization-key "GUID"`. По умолчанию организация **не
фильтруется**, поэтому этот параметр важен, если список 1С ограничен одной
организацией. Отдельный файл отчёта сохраняется в UTF-8.

Сканер считает кандидатом ЭСФ только при одновременном выполнении двух
проверок: `СчетФактура` пустое и `СчетФактура_Type` равно
`StandardODATA.Undefined`. Неоднозначные комбинации выводятся в `anomalies`.
Перед автоматизацией записи обязательно сверить выборку со списком в 1С.

## Предполётная проверка одного ЭСФ

Выберите **один** `ref_key` и `number` из `pending_esf.json`, который также
виден в открытом списке 1С. Команда читает заголовок, обе потенциальные
разновидности номера поставки и табличную часть `Товары`. Не создаёт документов:

```powershell
python esf_preflight.py --ref-key "GUID_ИЗ_ОТЧЕТА" --expected-number "НОМЕР_ИЗ_ОТЧЕТА" --output esf_preflight.json
```

Сверьте значения полей `ДокументПодтверждающийПоставкуНомер` и
`ДокументПодтверждающийПоставкуАВРНомер` с полем F. Документы поставки / Номер
в интерфейсе. Ссылка `ДоговорПоставки_Key` требует отдельного разрешения через
справочник договоров; совпадение текстового номера **не гарантирует** правильную
ссылку. Отчёт содержит значения реальных бухгалтерских полей — проверьте его
перед пересылкой.

Обновлённый preflight включает `Товар` и `Товар_Type` для каждой строки.
Номенклатуру создаём **только если отсутствует ссылка на неё**, независимо
от текстового наименования строки. Каждую из двух единиц измерения проверяем
отдельно: заполненные корректные ссылки не перезаписываем.

## Поиск договора в справочнике

Поиск ограничен номером договора и организацией; необязательный `--owner-key`
позволяет сузить выбор до контрагента. Если найдено несколько совпадений,
программа возвращает `ambiguous`: автоматически выбирать первый запрещено.

```powershell
python contract_lookup.py --number "ALA-58/2025 SD" --organization-key "57495537-f978-11ee-ad65-94de80502ae1" --output contract_lookup.json
```

Пока это **только чтение**. Никакие реквизиты договоров и документов не меняются.

Команда выводит только имена полей. Если нужно проверить значения одного документа, явно включить `--show-values` и при необходимости `--filter` по известному ID или номеру (синтаксис фильтра устанавливается по `$metadata`). Не публиковать вывод с персональными/финансовыми данными.

## Ограничения

- URL OData сформирован по официальной схеме 1С и пока не подтверждён успешным запросом в указанной базе.
- Текущий логин браузера не является гарантией успешной HTTP Basic-авторизации.
- Включение объектов в настройках 1С даёт потенциально более широкие полномочия, чем наш GET-only клиент; ограничьте серверные права отдельно, если доступно.
- Отображаемые в 1С кнопки «Создать на основании» и «Перезаполнить ссылочные реквизиты» не обязательно эквивалентны простым операциям OData.
- В фазе 1 не загружаем целиком список ЭСФ и не записываем локальные копии финансовых документов.
