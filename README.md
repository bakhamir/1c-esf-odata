# Автоматизация входящих ЭСФ в 1С:Фреш через OData

Проект для «Бухгалтерии для Казахстана», редакция 3.0. Цель — последовательно дополнять входящие ЭСФ недостающими учётными документами: полученным счётом-фактурой (СФ) и поступлением услуг, заполнять заданные реквизиты и проверять итоговые связи и проведение.

**Состояние на 26.10.2026:** чтение, проверки, исследования и офлайн-планировщики реализованы. Полного автоматического создания и проведения документов пока нет. Основное направление — **Python + стандартный OData**, без LLM в обычном пути исполнения.

## Текущая контрольная точка

- Подключение к OData производственной базы работает; исследованы metadata и реальные связи документов.
- Ранее успешно выполнен и проверен пользователем **один PATCH договора** в ЭСФ `28000019906`.
- Затем пользователь штатной командой интерфейса создал для этого ЭСФ полученный СФ. Проверка GET подтвердила: **СФ существует, связан с ЭСФ, записан без проведения, время 10:00:00**, организация, контрагент и договор правильные.
- Сам ЭСФ остался проведённым; среди наблюдаемых полей изменились только ссылка на СФ, её тип и версия данных. Дата, договор, строки и суммы сохранились.
- **Не создавать второй СФ для `28000019906`.** Дальнейшая работа с ним — подготовка поступления из существующего СФ.
- Офлайн-план поступления подготовлен: **12 кандидатов полей шапки и одна строка услуги**. Исполнителя создания/проведения пока нет; план заблокирован до разрешения оставшихся вопросов.
- Последний GET-поиск не обнаружил поступления по проверенной прямой ссылке на этот СФ. Это не исключает другие представления связи; перед будущей записью требуется повторная проверка.
- **86 unit-тестов проходят в основной ветке.** Тесты не обращаются к производственной базе.

Эти сведения — результаты выполненных проверок, а не постоянно обновляемое состояние базы.

## Основные достижения

1. **Безопасное чтение OData.** HTTPS, проверка сущностей и полей, чтение metadata, ограничение ответа, запрет перенаправления credentials.
2. **Поиск кандидатов.** Отбор ЭСФ по явным фильтрам, классификация отсутствующих/неоднозначных ссылок, контроль неполной выборки.
3. **Проверка одного документа.** Сверка ключа, номера, реквизитов и строк; точный поиск договора без выбора первого неоднозначного совпадения.
4. **Dry-run без записи.** Планы намерений, кандидаты полей, зависимости и явные блокирующие причины.
5. **Исследование реальных цепочек.** Изучены пять связанных ЭСФ/СФ/поступлений и затем начальное состояние СФ, созданного пользователем.
6. **Работа с данными без догадок.** Рекурсивное раскрытие типов строк metadata; сравнение многострочных документов по уникальным значениям, а не позиции; Decimal и сохранение точных строковых номеров.
7. **Продолжение уже связанного документа.** Отдельный план поступления проверяет существующий СФ и не пытается создать его повторно.
8. **Контроль наблюдаемого результата.** Офлайн-сравнение снимков ЭСФ до/после пользовательского создания СФ, без утверждения об отсутствии скрытых серверных эффектов.

## Производственная безопасность и scope

**База производственная, тестовой базы нет.** Текущий прототип ограничен:

- ТОО «Трансавиа»;
- датами ЭСФ **21.09.2026–13.10.2026 включительно**;
- одной организацией и контрагентом из [STATUS](docs/STATUS.md);
- договором **ALA-58/2025 SD**.

Все остальные организации, поставщики, периоды и договоры вне scope. Подписание и отправка в ИС ЭСФ запрещены.

- По умолчанию — офлайн-проверки и согласованные GET. На каждый новый вид и конкретный объём производственной записи нужно отдельное явное разрешение пользователя.
- Успешный PATCH договора и пользовательское создание СФ **не разрешают** создавать поступление, проводить документы или запускать массовую обработку.
- Исполнитель договора требует одновременно `--commit` и точный `--confirm`. Этот барьер нельзя обходить.
- Перед разрешённой записью — независимое перечитывание точной цели и проверка scope; после — проверка результата. При timeout/неясном ответе сначала исследовать побочные эффекты, не повторять POST вслепую.
- Один ЭСФ за раз. Не переносить номера, даты и ключи эталона в другой документ.
- Некоторые старые CLI ещё принимают произвольный scope: общий фиксированный барьер профиля для всех входных точек остаётся задачей. Не расширять scope через параметры.

`ready_for_review` означает готовность проекта к рассмотрению, а не разрешение на выполнение. `blocked` означает, что данные или семантика пока недостаточны. Кандидаты с `execution_supported=false` и `payload_complete=false` нельзя отправлять как готовые API-запросы.

## Архитектура и реализованные модули

Основная ветка использует **Python 3.12+**, стандартную библиотеку и `unittest`.

| Компонент | Реализовано |
| --- | --- |
| `odata_client.py` | GET, сущности, схема верхнего уровня, образцы, парсинг ответов |
| `esf_scanner.py` | Поиск несвязанных ЭСФ, фильтры, пагинация, аномалии |
| `esf_preflight.py` | Чтение и проверка одного конкретного ЭСФ |
| `contract_lookup.py` | Поиск точного договора с контролем неоднозначности |
| `config.py`, `processor/planner.py` | Бизнес-правила и чистый план намерений |
| `main.py` | Офлайн-план одного документа; GET-перечитывание очереди для dry-run |
| `execute_contract.py`, `processor/executor.py` | Preview и отдельно подтверждаемый PATCH одного поля договора |
| `reference_inspector.py` | GET-инспекция связанного СФ, scope, отсутствующие/null-поля, диагностика неполных ответов |
| `processor/invoice_planner.py`, `plan_invoice.py` | Офлайн-план первоначального СФ, раскрытие схемы строк, кандидаты и blockers |
| `processor/invoice_evidence.py` | Сравнение нескольких пар, точные числовые проверки, каталожные ссылки |
| `processor/creation_observer.py`, `observe_invoice_creation.py` | Сравнение сохранённых снимков вокруг штатного создания СФ |
| `processor/receipt_planner.py`, `plan_receipt.py` | Офлайн-продолжение существующего СФ: план поступления услуг |
| `tests/` | Mock/фиктивные клиенты и синтетические обезличенные fixtures |

Инспектор сам не читает поступление и не сверяет поля с metadata: его `schema_verified=false` / `receipt_inspected=false` описывают возможности именно этого отчёта. Более глубокое исследование схемы и поступлений выполнено отдельно и отражено в документации.

## Что показало исследование

- Ссылка ЭСФ на СФ представлена парой `СчетФактура` / `СчетФактура_Type`. В существующих завершённых цепочках СФ и поступление имеют взаимные основания.
- Во всех пяти изученных парах совпали организация, контрагент, валюта и итог документа. В одной паре договор СФ/поступления отличается от ЭСФ — такой образец исключается из подтверждения правил строк.
- В исследованных строках сумма СФ соответствует сумме **без налогов** ЭСФ; сумма СФ + НДС соответствует итогу строки ЭСФ. Одноимённые поля нельзя просто копировать без проверки смысла.
- Входящий номер **СФ** соответствует номеру ЭСФ. Входящий номер **поступления** по требованиям должен быть номером поставки из раздела F — это разные значения.
- КПН «НУ» в исследованной схеме — `УчитыватьКПН=true` и отдельный `ВидУчетаНУ_Key`, а не строка «НУ» в Boolean.
- Для требуемых статьи затрат, подразделения и вида учёта НУ найдены точные существующие справочные записи. Существующая единица имеет представление `Усл.` и полное наименование «Одна услуга»; отдельной `Усл` в выполненном точном поиске нет. Дубликат не создавался.
- В двух исторических поступлениях входящая дата отличается от требования использовать дату СФ; в одном — другая статья затрат. План следует SPEC, а не копирует эти отклонения.
- Metadata публикует `Post/Unpost`, но не раскрывает штатную команду создания СФ/поступления на основании. Создание через OData **не доказано эквивалентным** прикладной логике формы.

Это наблюдения ограниченной выборки, не универсальные правила для всех поставщиков, НДС и документов.

## Что ещё необходимо реализовать

| Исходное требование | Текущее состояние |
| --- | --- |
| Отбор и проверки ЭСФ | Реализованы; общий scope-барьер старых CLI требует усиления |
| Договор | Единичный PATCH реализован и ранее проверен |
| Номер поставки из F | Точная строка извлекается; соответствие форме ещё требует подтверждения |
| Перезаполнение ссылочных реквизитов | Семантика и выполнение не реализованы |
| Подбор/создание недостающей номенклатуры и обеих единиц | Частично исследованы; исполнителя записи нет |
| Автоматическое создание СФ и присоединение к ЭСФ | Есть офлайн-кандидаты и штатный пользовательский эталон; OData-исполнителя нет |
| Поступление услуг, КПН, БУ1/БУ3, входящие реквизиты | Офлайн-план готов; создание и заполнение не реализованы |
| Проведение поступления → СФ → ЭСФ | Не реализовано; требуются отдельные разрешения и проверка учётного результата |
| Журнал и восстановление после сбоя | SQLite-журнал и блокировка процесса ещё не реализованы |
| Полная итоговая проверка и партии | Только после доказанного единичного цикла и отдельного согласования |

Старый исполнитель PATCH дополнительно требует актуального GET-чтения самого договора и сравнения защищаемых полей до/после.

## Ближайший этап по OData

Продолжаем работу **из существующего непроведённого СФ** ЭСФ `28000019906`. Новые документы сейчас не разрешены.

План поступления остаётся заблокирован по семи причинам:

1. `receipt_creation_semantics_unverified` — семантика штатного создания не доказана для POST.
2. `receipt_initial_defaults_unverified` — нет проверенного первоначального образца поступления.
3. `created_receipt_date_unknown` — собственная дата будущего поступления неизвестна.
4. `receipt_invoice_backlink_effects_unverified` — порядок и эффекты обновления взаимных оснований неизвестны.
5. `supply_field_ui_mapping_unverified` — соответствие номера разделу F требует подтверждения.
6. `accounting_defaults_not_verified` — остальные счета и учётные defaults не установлены.
7. `recovery_journal_not_implemented` — журнал восстановления отсутствует.

Далее: уточнить начальную модель поступления и сохранение defaults, реализовать журнал восстановления, подготовить полный preview одной конкретной OData-операции. Если потребуется штатный пользовательский образец или контролируемая запись, сначала отдельно согласовать точную операцию. Прежний план диагностического создания поступления **ещё не выполнен и не разрешён**.

Итоговые требования остаются неизменными: сохранять собственные даты СФ и поступления, менять только время на 10:00:00; входящая дата поступления — дата СФ, входящий номер — точный номер поставки; НУ, БУ1 «Расходы по перелету», БУ3 «Основное подразделение»; прочие учётные параметры не менять. После проверки — отдельно разрешённые проведение, подтверждение отгрузки и итоговая сверка всех связей.

## Запуск локальных проверок

```powershell
python -m unittest discover -s tests -q
```

Офлайн-план одного ЭСФ из ранее сохранённых файлов:

```powershell
python main.py plan-one --preflight esf_preflight_v2.json --contracts contract_lookup.json --output dryrun_one.json
```

Офлайн-исследование первоначального СФ:

```powershell
python plan_invoice.py --metadata reports/metadata.xml --target reports/target_esf_raw.json --source reports/linked_esf_raw.json --invoice reports/invoice_raw.json --output reports/initial_invoice_plan.json
```

Эта команда рассчитана на **ещё не связанный** целевой ЭСФ; после создания СФ для `28000019906` её нельзя использовать для повторного создания. Дополнительные сохранённые пары передаются через `--pair`, справочники — через `--catalogs`.

Офлайн-план поступления для существующего СФ:

```powershell
python plan_receipt.py --metadata reports/metadata_final.xml --esf reports/receipt_source_esf.json --invoice reports/receipt_source_invoice.json --reference-invoice reports/deep_0_invoice.json --reference-receipt reports/receipt_reference_0.json --catalogs reports/receipt_catalogs.json --existing-receipts reports/receipt_existing_candidates.json --output reports/receipt_plan.json
```

Указанные JSON — частные локальные отчёты, их нет в Git. Для тестов и этих офлайн-команд учётные данные не нужны. Числа в кандидатах строк представлены точным десятичным текстом для просмотра, а не готовым HTTP JSON.

## Учётные данные и частные результаты

Для согласованных обращений к базе используются локальные `ONEC_ODATA_USERNAME` и `ONEC_ODATA_PASSWORD`; необязательная `ONEC_APP_URL` задаёт URL приложения. Не помещать credentials в код, историю команд, Git или чат. Пользовательские переменные Windows и окружение уже запущенного процесса могут различаться.

`reports/`, JSON/CSV, журналы, `.env` и `.venv` исключены из Git. Реальные снимки, ключи создаваемых документов и планы с бухгалтерскими значениями остаются локально. В тестах — синтетические данные. Не сохранять и не публиковать cookies, токены и необезличенные скриншоты.
