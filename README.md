# Автоматизация входящих ЭСФ через OData 1С:Фреш

Продолжение Python-прототипа для «Бухгалтерии для Казахстана» 3.0.
Python 3.12+, стандартная библиотека, unittest. Полный цикл создания и проведения документов пока не реализован.

## Безопасность и область применения

База **производственная**, тестовой базы нет. Прототип ограничен ТОО «Трансавиа», датами ЭСФ **21.09.2026–13.10.2026 включительно**, одной организацией и договором `ALA-58/2025 SD`. Точные идентификаторы — в [STATUS](docs/STATUS.md). Подпись и отправка в ИС ЭСФ исключены.

Каждая производственная запись требует отдельного явного согласования конкретного действия и документа. Исторически подтверждён один PATCH поля договора; он не разрешает последующие записи и не означает завершения ЭСФ.

Некоторые CLI принимают произвольный scope: единый программный барьер профиля пока отсутствует. Не использовать их для расширения прототипа. `ready_for_review` означает готовность проекта к рассмотрению, а не разрешение на запись или подтверждённую возможность проведения.

Авторизация: локальные переменные `ONEC_ODATA_USERNAME`, `ONEC_ODATA_PASSWORD`; необязательная `ONEC_APP_URL` — URL приложения 1С:Фреш. Не сохранять секреты в коде и истории команд. Не передавать пароли, cookies и необезличенные отчёты. Для тестов и офлайн-плана авторизация не нужна.

## Реализовано

| Модуль | Возможности |
| --- | --- |
| `odata_client.py` | GET, metadata, сущности, поля верхнего уровня, образец; запрет перенаправлений |
| `esf_scanner.py` | Поиск несвязанных ЭСФ по явным фильтрам, пагинация, аномалии |
| `esf_preflight.py` | GET одного ЭСФ, сверка ключа/номера, реквизиты и строки |
| `contract_lookup.py` | Поиск точного договора, блокировка неоднозначности |
| `processor/planner.py` | Чистый dry-run: намерения и blockers, без HTTP |
| `main.py` | Офлайн-план одного ЭСФ либо GET очереди и dry-run |
| `execute_contract.py` | Preview одного PATCH договора; запись с `--commit` и точным `--confirm` |
| `processor/executor.py` | Один PATCH единственного поля, без автоматического повтора |
| `reference_inspector.py` | GET связанных ЭСФ/СФ, проверка scope, диагностический отчёт v2 |

Доступ OData и один PATCH ранее проверены пользователем. В текущем этапе выполнялись только офлайн-проверки; исторические количества документов не являются актуальным подсчётом.

## Тесты и офлайн-план

```powershell
python -m unittest discover -s tests -q
python main.py plan-one --preflight esf_preflight_v2.json --contracts contract_lookup.json --output dryrun_one.json
```

На 26.10.2026: **71 тест проходит**, внешние вызовы заменены mock/фиктивными клиентами. Сообщение о неверном подтверждении в тестах ожидаемо: проверяется защитный барьер.

План содержит `blocked`, `ready_for_review`, `skip_already_linked`; GET-пакет может вернуть `read_error`. `prepare_*` — намерения, не готовые payload. План одного ЭСФ пока не проверяет фиксированный период прототипа. Пакетный dry-run читает производственную базу и не запускается автоматически.

JSON/CSV и каталоги отчётов исключены из Git. Отчёты могут содержать бухгалтерские значения: хранить локально, обезличивать перед передачей.

## Исследование эталона: GET после согласования чтения

Следующая команда обращается к производственной базе и сохраняет частный локальный отчёт:

```powershell
python reference_inspector.py --from-date 2026-09-21 --to-date 2026-10-13 --organization-key "57495537-f978-11ee-ad65-94de80502ae1" --counterparty-key "b711f358-7da3-11f0-8757-52540067a9c9" --limit 1 --output reference_invoice.json
```

`limit` ограничивает исследуемые связанные СФ (1–5); первоначальный GET читает до 200 заголовков ЭСФ scope. Потенциально усечённый ответ или continuation останавливают инспекцию. Локально проверяются дата ЭСФ, ключи, организация и поставщик. Дата связанного СФ не обязана совпадать с датой ЭСФ.

Отчёт v2 различает отсутствующие поля, null и присутствующие табличные части; отмечает неподдержанные связи. Отсутствие контрагента СФ отмечается как непроверенное, явное несовпадение останавливает чтение. `schema_verified=false`, `receipt_inspected=false`: поступление и metadata ещё не исследуются. Предполагаемые поля не подтверждены схемой. Ключи, номера и даты образца нельзя переносить в новый документ.

## Что остаётся сделать

Нет проверенных аналогов команд создания на основании, перезаполнения и проведения; payload СФ/поступления; lookup всех справочников; журнала восстановления и массового исполнителя. Старый PATCH требует усиления: фиксированный scope, актуальное GET-чтение договора и сравнение реквизитов до/после. При неопределённом результате записи сначала исследовать сервер, не повторять создание вслепую.

## Офлайн-план первоначального СФ

Реализован отдельный диагностический этап (71 unit-тест). Команда читает только локальные файлы и не требует авторизации:

```powershell
python plan_invoice.py --metadata reports/metadata.xml --target reports/target_esf_raw.json --source reports/linked_esf_raw.json --invoice reports/invoice_raw.json --output reports/initial_invoice_plan.json
```

Отчёт содержит раскрытую схему строк, присутствие полей, наблюдения по одной строке эталона, кандидаты трёх реквизитов шапки и блокирующие неизвестные. Это ещё не POST payload: status=blocked, payload_complete=false, execution_supported=false. Файл содержит частные ключи целевого документа и номер поставки; хранить только локально, не отправлять в Git.

## Углублённое исследование и планировщик v2

Сравнение нескольких локальных пар: повторяйте `--pair путь_ЭСФ путь_СФ` для дополнительных **различных** ЭСФ. `--catalogs` принимает локальный JSON-объект с именами справочников и массивами сохранённых записей. Все эти файлы частные и должны оставаться в reports/.

План проверяет согласованность договоров, уникально сопоставляет строки по значениям, проверяет каталожные ссылки цели и сохраняет исходные восемь блокеров. Кандидаты строк содержат числа как точный десятичный текст для рассмотрения; это не готовый HTTP JSON. Ошибка договора эталона и расхождение Усл./Усл выводятся отдельно. Текущая проверка: **71 тест проходит**. Подробности: [DEEP_INVOICE_RESEARCH](docs/DEEP_INVOICE_RESEARCH.md).

## Продолжение существующего СФ: поступление услуг

`plan_receipt.py` готовит офлайн-кандидаты поступления по уже связанному непроведённому СФ. Повторного СФ не создаёт; существующие основания/поступления блокируют новую подготовку. Дата входящего документа берётся из СФ, номер — из поставки ЭСФ, дата самого поступления остаётся зависимостью. КПН и субконто проверяются по типам/точным справочникам. Старые счета и default-реквизиты не копируются. Это не POST payload и не исполнитель. Все **86 тестов проходят**. Подробнее: [RECEIPT_CONTINUATION](docs/RECEIPT_CONTINUATION.md).
