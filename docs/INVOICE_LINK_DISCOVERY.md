# Исследование создания связи полученный СФ ↔ ЭСФ

26.10.2026. Статус: подготовка GET-исследования; production GET ещё не выполнялись.

## Что подтверждено документацией платформы

- Стандартный OData позволяет создавать объекты через POST и обновлять через PATCH/PUT. Проведение является отдельной операцией. Источник: https://www.1cfresh.com/articles/data_odata (разделы 2.3, 7).
- Платформа вызывает обработчики событий и проверяет права, но не выполняет проверки заполнения через стандартный REST. Это требует независимой валидации клиента. Источник: https://1c-dn.com/1c_enterprise/rest_interface/ .
- Правила заполнения при создании на основании определяются прикладным решением. Источник: https://1c-dn.com/library/user_manual_generating_objects_based_on_other_objects/ .

Вывод для проекта: эти источники не доказывают доступность команды «Создать счёт-фактуру» для ЭСФ БК Казахстан 3.0 через OData. Нельзя утверждать, что POST СФ автоматически заполнит ЭСФ.СчетФактура или что ручная установка ссылки воспроизведёт побочные эффекты штатной команды.

## Ограниченный план чтения

После доступности авторизации выполнять последовательно, только GET:

1. Один запрос $metadata. Сохранить локально в игнорируемом reports/. Не выводить полный XML в чат. Выделить поля и типы Document_ЭСФ и Document_СчетФактураПолученный, зависимые типы строк и опубликованные FunctionImport. Проверить реальные способы представления составных ссылок.
2. Один GET заголовков ЭСФ только подтверждённого профиля, периода и без пометки удаления, до 200 записей. Неполнота ответа блокирует выводы. Из уже связанных выбрать один детерминированный пример. Не брать другой период, если пример отсутствует.
3. Один GET выбранного СФ по точному ключу. Проверить идентичность, организацию и поставщика. Сохранить сырой образец только локально; в диагностике показывать названия полей, типы, присутствие и результаты сравнений, а не бухгалтерские значения.
4. По подтверждённой схеме найти обратные ссылки на ЭСФ: проверить заголовок, табличные части, опубликованные связи/регистры, если они действительно требуются. Не сканировать все СФ или регистры в поиске похожего номера. Дополнительные точечные GET определяются результатами первых трёх шагов.
5. Перечитать ранее исправленный ЭСФ по известному точному ключу, убедиться в scope, договоре, отсутствии СФ и достаточности полей. Никакого изменения целевого ЭСФ.

## Таблица вопросов для принятия решения

| Вопрос | Доказательство | Пока неизвестно |
| --- | --- | --- |
| Как хранится ЭСФ.СчетФактура? | metadata + значение/тип существующего примера | GUID, составная ссылка, необходимость пары _Type |
| Ссылается ли СФ обратно на ЭСФ? | metadata и сопоставление с ключом того же ЭСФ | Точное поле/табличная часть/регистр |
| Есть ли опубликованная операция создания на основании? | FunctionImport и официальная семантика | Наличие операции в данной публикации |
| Какие реквизиты нужны новому СФ? | Схема, образец, подтверждённые правила конфигурации | Минимальный корректный payload и defaults |
| Когда заполняется связь ЭСФ? | Документированная конфигурационная логика; одного снимка недостаточно | POST, запись/проведение СФ либо отдельное действие |
| Есть ли дополнительные эффекты штатной команды? | Документация/анализ доступной логики конфигурации | Регистры, статусы, служебные ссылки |

Снимок существующей пары показывает структуру, но не порядок её создания. Если GET/официальных материалов недостаточно для доказательства побочных эффектов, это остаётся blocker; не проверять догадки производственным POST.

## Ожидаемый результат

Карта связи, список подтверждённых полей и неизвестных эффектов, затем чистый офлайн-план одного ЭСФ: create_received_invoice и зависимости следующей стадии. Прямой PATCH связи добавлять в план только после доказательства его необходимости и корректности. Не выбирать дату автоматически из ЭСФ; сохранить политику SPEC для даты созданного СФ и времени 10:00:00. Не копировать ключи/номера образца.

Запись и проведение остаются отдельными будущими согласованиями. Текущая работа не вводит исполнитель POST.

## Результаты ограниченных GET (26.10.2026)

Авторизация проверена без вывода credentials. Выполнено 7 GET: metadata; заголовки scoped ЭСФ; связанный СФ инспектором; повторное полное чтение этого СФ; его ЭСФ; целевой ЭСФ; поступление по точному основанию СФ. Записей не было. Сырые ответы сохранены только в игнорируемом reports/.

Подтверждено на одном примере:

- ЭСФ.СчетФактура имеет Edm.String; парное СчетФактура_Type — Edm.String. Значение ссылки выбранного примера разбирается как GUID полученного СФ.
- СФ имеет поля организации, контрагента, договора, дат, подтверждения отгрузки; все ожидаемые инспектором поля присутствуют. Контрагент и организация совпали.
- У СФ одна строка Услуги и одна строка ДокументыОснования; Товары пусты. СФ.ДокументОснование и основание в табличной части указывают на одно поступление типа StandardODATA.Document_ПоступлениеТоваровУслуг.
- Поступление.ДокументОснование, наоборот, указывает на этот СФ: есть взаимные ссылки СФ ↔ поступление. Организация/контрагент совпали; оба документа проведены и не помечены на удаление.
- В значениях полей/строк прочитанного СФ не обнаружено прямого совпадения с ключом исходного ЭСФ. Это не доказывает отсутствие других механизмов связи (например, регистров).
- Для ЭСФ и полученного СФ в metadata обнаружены связанные операции Post/Unpost. Опубликованная операция создания/заполнения на основании для этих двух типов не обнаружена. Ничего не вызывалось.
- Целевой ЭСФ остаётся в согласованном периоде/организации/поставщике; договор правильный, связь с СФ отсутствует.

Вывод: структура связи подтверждена, но порядок её формирования и побочные эффекты штатной команды ещё неизвестны. Нельзя копировать финальный СФ как POST-шаблон: он уже содержит ссылку на поступление, которого на начальной стадии ещё нет. Нужен staged offline-план: первоначальный СФ с явно неизвестными defaults/датой, затем поступление и только доказанные обновления взаимных ссылок. Даже прямой PATCH ЭСФ.СчетФактура пока является гипотезой, а не подтверждённым эквивалентом команды интерфейса.

Следующая разработка без записи: извлечь полную карту типов строк из сохранённого metadata, сопоставить строки исходного ЭСФ и СФ, составить allowlist полей и blockers для первоначального СФ. Для установления момента заполнения ссылок нужен подтверждённый алгоритм конфигурации либо отдельно согласованное наблюдение стадий штатного создания; существующий конечный снимок этого не доказывает.

## Наблюдения офлайн-сопоставления строк

В единственной исследованной паре совпали номенклатура, количество, цена, НДС, ставка НДС и оборот. Содержание СФ отличается от ТоварНаименование ЭСФ. Сумма СФ отличается от Сумма ЭСФ, но совпадает с СуммаБезНалогов ЭСФ; Сумма СФ + СуммаНДС СФ совпадает с Сумма ЭСФ. Проверка выполнена локально с Decimal, реальные значения не публикуются. Это наблюдение одного примера, не универсальное правило для смешанного НДС или нескольких строк; прямое копирование одноимённой Сумма запрещено до подтверждения налоговой семантики.
