# Продолжение существующего СФ и подготовка поступления

## Реализовано

Планировщик processor/receipt_planner.py и CLI plan_receipt.py работают только с сохранёнными файлами. У существующего связанного СФ проверяются организация/поставщик/договор, непроведённое состояние, отсутствие оснований, совпадение строк и сумм с ЭСФ. Он не вызывает старый план создания СФ и явно возвращает create_invoice_again=false.

Для текущего ЭСФ 28000019906 подготовлены 12 кандидатов шапки и одна строка услуги. Числа представлены точным десятичным текстом для просмотра, не HTTP JSON. Header Date отсутствует: дату будущего поступления сохраняем собственную, время 10:00:00. Входящая дата строится из календарной даты уже созданного СФ (Edm.DateTime с временем 00:00:00 для поля даты); не из текущей даты, не из ЭСФ и не из исторического поступления. Номер поставки сохраняется точной строкой из одного непустого поля F, без trim/преобразования числа.

Кандидаты: организация, поставщик, договор, валюта и основание существующего СФ; вид операции Услуги; УчитыватьКПН=true плюс ВидУчетаНУ_Key точной записи НУ; вид входящего документа Акт выполненных работ; номер поставки и дата СФ. Строки берутся из существующего СФ: номенклатура, количество, цена, сумма, НДС/ставка и содержание; БУ1 и БУ3 берутся из точных lookup Расходы по перелету и Основное подразделение. Строковые составные ссылки имеют парный _Type. Чужие счета, БУ2/НУ и прочие параметры образца не копируются.

## GET в этом этапе

8 последовательных GET: ЭСФ, его существующий СФ, поиск поступлений по точной обратной ссылке СФ, два точных исторических поступления, три точных поиска справочников НУ/статья/подразделение. СФ остаётся непроведённым; поступлений по проверенной прямой обратной ссылке не найдено. Это не абсолютное доказательство отсутствия документа с другим видом связи. Пользовательских записей или агентских мутаций не было.

В обоих исторических поступлениях подтверждены типы субконто, операция Услуги, КПН Boolean=true и ссылка на НУ, строковый вид входящего документа. Но входящая дата обоих не соответствует требованию даты СФ, а статья затрат одного — не требуемая. Planner регистрирует reference_deviations и использует SPEC, не исправляя исторические документы.

## Текущие семь блокеров поступления

- receipt_creation_semantics_unverified — команда создания на основании не доказана как POST.
- receipt_initial_defaults_unverified — нет образца нового непроведённого поступления после штатного заполнения.
- created_receipt_date_unknown — собственная дата поступления ещё не известна.
- receipt_invoice_backlink_effects_unverified — когда и как обновляются взаимные основания, не доказано.
- supply_field_ui_mapping_unverified — пользователь должен подтвердить номер именно раздела F.
- accounting_defaults_not_verified — счета/остальные параметры нельзя заимствовать из другого документа.
- recovery_journal_not_implemented — журнал восстановления ещё не реализован.

Это blockers **следующей стадии**, а не утверждение о снятии всех общих blockers будущего автоматического создания СФ для других ЭСФ. Для текущего существующего СФ дата известна и начальное состояние наблюдалось, повторное создание исключено.

## Локальная команда

```powershell
python plan_receipt.py --metadata reports/metadata_final.xml --esf reports/receipt_source_esf.json --invoice reports/receipt_source_invoice.json --reference-invoice reports/deep_0_invoice.json --reference-receipt reports/receipt_reference_0.json --catalogs reports/receipt_catalogs.json --existing-receipts reports/receipt_existing_candidates.json --output reports/receipt_plan.json
```

Сырые файлы и план с ключами/номерами сохраняются только в игнорируемом reports/. Каталоги — объект с именами сущностей и массивами строк. existing-receipts — полный сохранённый ответ точного поиска; continuation/усечённость отклоняются. Наличие любого найденного поступления, в том числе помеченного на удаление, блокирует создание, а не вызывает повтор.

## Предлагаемый следующий опыт — НЕ разрешён и НЕ выполнен

Запросить отдельное подтверждение на одно штатное создание пользователем поступления из **существующего СФ** ЭСФ 28000019906:

1. До команды агент повторяет GET точного ЭСФ, СФ и поиск возможного поступления; при расхождении/существующем основании остановиться.
2. В существующем СФ выбрать Создать на основании → Поступление ТМЗ и услуг → Услуги (акт) → Выбрать. При предупреждении, неизвестном выборе или требовании проведения — остановиться до следующего подтверждения.
3. Сохранить дату нового поступления, выбранную 1С, изменить только время на 10:00:00. Не подставлять дату СФ как дату самого поступления.
4. НУ, БУ1 Расходы по перелету, БУ3 Основное подразделение; остальные счета и параметры оставить заполненными штатной командой. Не создавать справочники, не менять другие документы.
5. Входящий тип Акт выполненных работ; входящий номер — точный номер раздела F исходного ЭСФ с ведущими нулями/разделителями; входящая дата — календарная дата существующего СФ. Проверить соответствие формы до сохранения, не присылать конфиденциальные значения в чат.
6. **Один раз Записать без проведения.** Этот диагностический промежуточный шаг не заменяет итоговое требование Провести и закрыть: проведение будет отдельно согласовано после GET-верификации. СФ не проводить, подтверждение отгрузки пока не включать; ЭСФ не перепроводить/не отменять проведение.
7. Возможное автоматическое обновление оснований СФ штатной командой входит в согласуемый опыт. По завершении агент читает точные документы, сравнивает строки/даты/аналитику/ссылки и сохранённые default-счета. Получится начальный эталон поступления для офлайн-модели, а не доказательство эквивалентности OData POST.

Никаких автоматических OData записей, повторных СФ, проведения, отправки/подписания, удаления или отката в этом опыте. При timeout/неясном результате кнопки сначала GET и проверка уже созданного; никакого повторного создания. Любое исправление требует отдельного согласования.

После такого образца: уточнение полной модели полей и сохранения defaults, журнал восстановления, проверка preview одной конкретной OData операции, отдельное разрешение, только потом дальнейшая запись и проведение в порядке SPEC.
