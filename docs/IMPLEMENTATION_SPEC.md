# ТЗ дальнейшей реализации автоматизации ЭСФ

26.10.2026. Инженерное продолжение SPEC. Документ не разрешает производственные операции и не заменяет AGENTS, SPEC и явные указания пользователя.

## Цель и границы

Детерминированно завершать связанные документы одного входящего ЭСФ: проверить договор, номенклатуру и единицы, создать полученный СФ и поступление услуг, заполнить заданные реквизиты, провести в согласованном порядке и подтвердить учётный результат. В обычном пути исполнения LLM не используется.

Прототип: только ТОО «Трансавиа», организация/контрагент/договор из STATUS, даты ЭСФ 2026-09-21..2026-10-13 включительно. Расширение scope — отдельная задача пользователя. Подпись/отправка ИС ЭСФ, прямой SQL, права и конфигурация исключены. База производственная, тестовой базы нет.

## Исходное состояние и проблемы

Есть GET-клиент, сканер, preflight, поиск договора, планировщик намерений, единичный PATCH договора и инспектор связанного СФ. 49 unit-тестов проходят офлайн. Историческая запись подтверждена пользователем; новых live-проверок не выполнялось. Зелёные тесты не доказывают эквивалентность OData командам интерфейса.

| Проблема | Решение | Критерий приёмки |
| --- | --- | --- |
| Scope доверяется отчётам | Общий фиксированный профиль для planner/inspector/executor | Чужая организация, поставщик, период или договор блокируются до внешнего вызова |
| Договор берётся из локального снимка | GET точного договора перед записью: владелец, организация, номер, удаление/папка | Устаревший договор блокирует действие |
| После PATCH проверяется лишь ссылка | Сравнивать защищаемые поля и строки до/после, отдельно учитывать технические поля сервера | Неожиданное изменение останавливает сценарий |
| Имена полей пока предполагаются | Карта metadata и обезличенных образцов | Неизвестный тип/поле блокирует план |
| Нет чтения поступления | GET только по подтверждённым типизированным связям СФ | Никакого выбора по похожему номеру |
| Справочники не разрешены | Точный lookup единиц, номенклатуры и аналитик | Ноль/несколько совпадений блокируют выбор |
| План содержит лишь намерения | Чистый planner payload с источником каждого значения | Нет HTTP и копирования ключей эталона |
| Неизвестны даты новых документов | Явные зависимости от фактически прочитанных дат | Неизвестная дата оставляет план частичным |
| Нет восстановления | SQLite, блокировка процесса, намерение до запроса, сверка после сбоя | Повторный запуск не создаёт дубликат |
| HTTP успех не доказывает проведение | Проверять связи, статусы и согласованный учётный результат | completed только после полной сверки |

## Этап A. Исследование схемы и связей

1. Разобрать обезличенный отчёт одного существующего связанного ЭСФ. При отсутствии отдельно согласовать узкие GET. Не читать базу автоматически.
2. Изучить metadata: EntityType, ComplexType строк, nullable, точность чисел, длины строк, NavigationProperty, опубликованные действия. Текущий entity_schema раскрывает только верхний уровень; расширять совместимо либо версионировать формат.
3. Проследить ЭСФ → полученный СФ → поступление. Проверять тип/ключ каждой связи, организацию, поставщика, признаки удаления. Период применять к ЭСФ, не навязывать его связанным документам. Несколько возможных оснований — blocker.
4. Определить поля СФ: дата, организация, поставщик, договор, входящие реквизиты, подтверждение отгрузки, основания и связь с ЭСФ. Для поступления: вид операции услуг, дата, входящий тип/номер/дата, строки услуг, КПН, БУ1/БУ3, остальные сохраняемые параметры и связи.
5. Составить карту «бизнес-требование → поле → тип → источник → проверка → статус подтверждения». Значение образца не доказывает обязательность POST и не раскрывает серверные defaults.
6. Проверить семантику создания на основании, перезаполнения и проведения по опубликованным возможностям. Если OData не обеспечивает требуемых эффектов, зафиксировать ограничение и согласовать альтернативу; не подменять команду неподтверждённым PATCH и не менять права/публикацию.

Результат: карта полей/связей, список неизвестных эффектов, синтетические fixtures. GET-инспектор не выдаёт неполный ответ за полное исследование. Текущий v2 — диагностический вход, не подтверждённая карта схемы.

## Этап B. Справочники и офлайн-planner payload

Вход: один проверенный ЭСФ, снимок схемы, подтверждённые справочные ключи, профиль; при необходимости фактические даты созданных документов. Сбор входа отделён от planner. Planner не содержит клиента, credentials и отправки запросов.

Выход: версионированный план одного ЭСФ, blockers, зависимости, предлагаемые поля и источники, предусловия/постусловия. Неполный план не готов к исполнению. Серверные ключи, номера и технические поля эталона не копировать.

- Номер поставки — раздел F; точная строка с нулями, пробелами и разделителями. Пустое, нестроковое или неоднозначное значение блокирует план. Соответствие поля разделу F должно быть подтверждено.
- Договор строго ALA-58/2025 SD. Правильный сохранять; другой существующий не заменять автоматически.
- Номенклатуру сначала искать среди подходящих существующих записей. Создание допустимо лишь после доказанного отсутствия подходящей и остаётся отдельной будущей операцией. Обе единицы проверять независимо, правильные не менять; целевая единица Усл.
- СФ и поступление: менять только время на 10:00:00, сохранять календарную дату каждого. Входящая дата поступления — дата полученного СФ, не запуска и не автоматически ЭСФ. Неизвестные даты описывать зависимостями.
- Услуги: КПН НУ, БУ1 Расходы по перелету, БУ3 Основное подразделение. Входящий тип Акт выполненных работ, номер из F. Другие параметры сохранять.
- Числа обрабатывать без float-потерь, округление по подтверждённым правилам. Полные табличные части сохранять там, где требует подтверждённый API. Сокращённый preflight не использовать как полную основу будущего PATCH.

Приёмка: детерминированные планы; негативные тесты scope, типов, дублей, отсутствующих полей и неизвестных дат; ведущие нули, разные даты СФ/поступления, сохранение посторонних полей. Ни одного POST/PATCH/проведения на этом этапе.

## Этап C. Журнал и восстановление

Локальная SQLite: ключ ЭСФ и scope, номер поставки, даты, связанные ключи, версия/хеш плана, текущая стадия, намерение операции, результат проверки, ошибка. Состояния: discovered, validated, planned, stage_pending, stage_verified, blocked, failed, state_unknown, completed.

Стадии: подготовка ЭСФ, создание СФ, создание поступления, проведение поступления, подтверждение и проведение СФ, проведение ЭСФ, итоговая сверка. Намерение фиксируется до запроса. Timeout/обрыв переводят в state_unknown: далее только чтение и проверка побочных эффектов. Автоматического повторного POST нет. Если состояние не восстановить однозначно — ручная проверка.

Один процесс и один ЭСФ одновременно. Номера/даты не переносятся между записями. Реальный журнал не попадает в Git. Приёмка: тесты сбоя до запроса, после серверной записи до локальной фиксации, повторного запуска и конкурирующего процесса, без реальной сети.

## Этап D. Отдельно согласованные единичные записи

Для каждого нового вида записи: конкретный ЭСФ, preview полей и ожидаемых эффектов, полный scope, отдельное явное согласие. Сохранить двойной CLI-барьер. Разрешение одной стадии не разрешает другие. Перед запросом перечитать цель/справочники и проверить отсутствие созданных связей. Контроль серверной версии применять только если подтверждён API. После каждого действия — GET и проверка.

Бизнес-порядок по SPEC: подготовка ЭСФ → СФ → поступление услуг → проведение поступления → подтверждение отгрузки и проведение СФ → проведение ЭСФ → итоговая проверка. Конкретные HTTP-команды и их порядок требуют результатов этапа A. Вместе с пользователем проверить учётный результат на согласованном примере. completed не равен HTTP 2xx.

Массовый режим вне текущей реализации. Обсуждать лишь после доказанного полного единичного цикла и отдельного разрешения: маленькие партии, остановка на неоднозначности, прогресс каждые пять завершённых ЭСФ.

## Порядок поставки

Небольшие коммиты: диагностика инспектора; общий scope и усиление старого PATCH без запуска; карта схемы/связей и GET поступления; lookup; чистый planner; журнал; отдельно согласованные стадии записи. Каждый этап обновляет STATUS/DECISIONS и проходит `python -m unittest discover -s tests -q`.

Не добавлять зависимости без обсуждения и не переписывать работающие модули без необходимости. Перед публикацией проверять diff и состав файлов: без секретов, сырых отчётов, PII и учётных payload. Доступы GitHub и видимость репозитория не менять.
